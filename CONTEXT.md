# Inkling Editor

A Lexical-based rich-text editor built around cards — block-level embeds (image, video, button, bookmark, …) that live inside the document but behave as atomic units.

## Language

**Card**:
A block-level embed in the document (image, video, gallery, button, bookmark, callout, toggle, header, file, audio, html, code block, horizontal rule, math). Atomic from the writer's perspective: selected as a unit, deleted as a unit. The table element family is deliberately not a card — its cells hold editable inline text with a real Lexical selection, which the decorator card pipeline cannot provide — so "card" never names tables.
_Avoid_: decorator, embed, block

**Card adjacency**:
The state of the caret or selection sitting immediately before or after a card. Comes in two notions: **visual adjacency** (the caret's rendered position, derived from geometry — what arrow keys care about) and **logical adjacency** (the selection anchor's offset — what backspace/delete care about).
_Avoid_: next-to-card, beside-card

**Card spec**:
The declarative definition of a card — its properties, card menu, nested editors, and transient state — from which the card's node behaviour is produced. Simple cards are nothing but their spec. The transient/nested-editor field vocabulary is single-sourced from the spec at the type level — names AND value types: the spec arrays are `as const satisfies` on the declaration, every transient entry's `initial` lambda annotates its return type (the field's value type), a nullable nested editor is built with `nullableNestedEditor` (a type-level brand carries `LexicalEditor | null`; plain literals derive a non-null editor), and `CardSpecFieldMap<typeof declaration>` (exported from the public barrel, defined beside the generator) derives the whole `__*` map. The map rides the assembled class's instance type (`assembleCardNodeOnce` folds it in), so the shims are re-exports plus their dataset types with no hand-written map or cast — renaming or retyping a spec entry is a compile error at every consumer. The base class's `declare __*` leg cannot derive (a base cannot import its declaration), so it stays the one hand-written site, pinned against the derived map by `test/typecheck/card-spec-field-agreement.ts`; `card-declarations.test.ts` pins the constructed/dataset agreement at runtime.
_Avoid_: card config, card definition

**Card declaration**:
The single per-card source of truth naming everything the editor must know about a card: its card spec, whether it joins the markdown round-trip (the `markdown` flag), its insert-command registration (command, edit-mode flag, media claiming), its toolbar label (`toolbarLabel` — the `data-inkling-card-toolbar` selector contract), and, for the four media cards, its `uploadType`. The declarations come from two sources read together: the closed built-in set `CARD_DECLARATIONS` and the host cards' registry (`getHostCards()`, src/nodes/cards/host-card-registry.ts). Every registry is a derived view over the card declarations — the node sets (`getEditorCardNodes`), the menus, the decorate targets, the insert registrar (`CardInsertPlugin`), the toolbar label (`getCardToolbarLabel`, beside the merge policy in card-facts), and the markdown fence payloads (src/nodes/cards/card-markdown-transformers.ts). Every derived view resolves its card facts through one merge-policy module — `resolveCardFacts` / `resolveAllCardFacts` (src/nodes/cards/card-facts.ts): built-in declaration first, host registry fallback, so the "host cards never override built-ins" invariant has exactly one home. The host registry stores the raw host spec (a neutral fact store), and both sources flow through the same per-view projectors — `resolveCardMenuEntries` / `resolveCardDragIcon` (card-menus), `resolveCardDecorateTarget` (card-decorate), the insert projection (card-insert-commands, which derives the host class through the same memoized assembler `defineCard` used) — so no projection is implemented twice. The layering rule behind the pipeline (declarations React-free, the registry layer never value-imports the wrapper layer, `getEditorCardNodes` off the wrapper registry) is pinned statically by `test/unit/nodes/card-layering-imports.test.ts`.
_Avoid_: card registration, card manifest

**Editor surface**:
One of the shipped top-level editor compositions — the default editor (`InklingEditor`) and the markdown round-trip. Each is a preset over the shared composer: its own node set (derived from `EDITOR_BASE_NODES`), its feature plugins (`DEFAULT_FEATURE_PLUGINS`), its markdown transformers. A card declaration's `markdown` flag names whether the card joins the round-trip; there is no runtime surface query — a card is present on a surface because that surface composed its node in. `InklingSurface` (src/components/InklingSurface.tsx) is the composition rule made exportable: a custom host surface wraps its top-level editor tree in exactly one (inside an `InklingComposer`), so nested card editors share the top-level undo stack and `onChange`. The published package layers the surfaces across two entries: `.` carries the full editor, while `./core` (plan C5) ships only the card-free composition pieces — the core `InklingComposer` (required `nodes`), `InklingSurface`, `InklingComposableEditor`, `RestrictContentPlugin`, and the `MINIMAL`/`BASIC` node and transformer sets.
_Avoid_: environment, platform

**Import spec**:
The card declaration's DOM-import knowledge — how the card's markup reads back into node state on HTML import/paste: declarative conversion entries (tag, priority, guard, per-property reads) defined beside the card's `properties` in its base node module, from which the generated node machinery derives `importDOM`. The generator throws at class-creation time when a read names an unknown property. Cards whose parsing is structural (collection payloads, sibling walking, DOM mutation, derived payloads) keep hand-written parsers.
_Avoid_: import parser, DOM conversion config

**Render context**:
The read-only, per-render-pass view of export-time policy and data that is the sole export-time view a card renderer receives besides the node: URL safety, sanitization, feature flags, color checks, document resolution, heading-id tracking, image/markdown data options, render-time meta resolution. The public entry points (`exportDOM(editor, options)`, `$convertToHtmlString`, `LexicalHTMLRenderer.render`) still accept the export options and build the context from them. Card sources must not import the policy modules directly — an import guard enforces the seam.
_Avoid_: options bag, policy object

**Headless HTML surface**:
The public headless conversion pair-plus-one (`lexicalStateToHtml` / `htmlToLexicalState` / `lexicalStateToPlainText`, src/html/headless-html.ts) — one stateless function per direction; the export function owns the render recipe directly (there is no internal renderer class — the former pass-through was deleted and the test suites drive this seam with an injected jsdom). The shared "assemble a headless editor" recipe lives in the **headless editor factory** (src/html/headless-editor.ts) with NAMED merge modes — `additive` (renderer/plain-text: caller nodes after `DEFAULT_HTML_NODES`, last registration wins) vs `wholesale` (importer: `editorConfig` replaces the defaults) — so the deliberate node-merge asymmetry is structural, not comment-carried. Both HTML directions resolve their DOM through the headless DOM port; the plain-text direction needs no DOM and stays synchronous. The import-side surgery is single-sourced in `$insertHtmlDocument` (src/html/html-to-lexical/insert-html.ts): root reset to one scaffold paragraph, `$generateNodesFromDOM`, `@lexical/clipboard`'s `$insertGeneratedNodes` normalization (which superseded the hand-rolled facebook/lexical#2807 empty-node filter), scaffold cleanup — the headless importer and `HtmlOutputPlugin`'s initial `html` prop run the identical body.
_Avoid_: renderer class export, HTML round-trip module

**Headless DOM port**:
The only module in the package that knows jsdom (src/html/headless-dom.ts): `resolveHeadlessDom(injected?, load?)` resolves the `ExportDOMDom` for one headless conversion — an injected `options.dom` first, then the global `window.document` (mirroring the render context's createDocument chain), then a lazily imported, process-cached JSDOM, throwing an error naming the optional `jsdom` peer on failure. The jsdom loader hides behind the `load` injection port, so the failure leg is a synchronous test table. No other module may import jsdom — an import guard enforces it.
_Avoid_: jsdom imports in conversion modules, per-module DOM sniffing

**Export-time image sizing**:
The one module owning export-time img dimension policy (src/nodes/base/utils/export-image-sizing.ts): `getExportImageDimensions` returns the resized width/height when the shrink policy applies (`defaultMaxWidth` set, the intrinsic width exceeds it, and the image is local and transformable) or `null` to keep intrinsic dims. The image and gallery renderers are the two adapters; their `sizes`-attribute rules stay per-card data.
_Avoid_: resize helper, sizing logic

**Card interaction**:
The headless select→edit choreography behind InklingCardWrapper (src/plugins/behaviour/card-interaction.ts): one stable registration per card nodeKey — the editor-level CLICK_COMMAND handler (editor-level so the card can pre-empt the editor's click without blocking its own React content) and the container's mousedown select-and-swallow. Selection/edit truth is read from the card selection store at event time, so registration never re-runs per render (the former no-dep-array effect re-registered a LOW-priority command every render). Guards are data: click-through zones, the settings panel, input/textarea focus passthrough. The wrapper keeps only the render, the card-type init read (published to the subtree through CardContext's `cardType` — `useCardToolbarLabel` reads it instead of an un-subscribed render-time editor read), and the width dataset marker.
_Avoid_: click handler in the wrapper, card click choreography

**Card write seam**:
The typed write path for card-node fields: `$updateCardNode(nodeKey, guard, update)` (src/nodes/base/update-card-node.ts), called inside `editor.update()`. The card's own `$is*` guard narrows the node, so every field the mutator writes is checked against the card's node type. The React-side invocation idiom has one home beside the seam: `useCardWriter(nodeKey, guard)` (src/hooks/useCardWriter.ts) owns `editor.update` + `$updateCardNode` + the guard and returns a `write(mutator)` the card component calls per mutation — the five-line ceremony is never re-typed at a call site.
_Avoid_: `$getNodeByKey` + `as GeneratedDecoratorNodeBase`

**Card selection store**:
The per-top-level-composer, editor-side store owning card-selection truth for non-React code: the selected card key and the edit-mode flag. Built on the composer handle factory; fed by registerCardSelection and the card command handlers, read synchronously by command handlers, subscribed to render-only by React via useCardSelectionState. There is no per-feature selection context — the former `InklingSelectedCardContext` folded into this store.
_Avoid_: selection context, selection mirror, selected-card state

**Composer handle**:
A per-top-level-composer, editor-side channel in the card-selection-store shape (getState / setState(partial) / subscribe, reference-equality change guard, render-only useSyncExternalStore binding, one provider-created instance with a module-default fallback) for values non-React code must read synchronously. One factory owns the pattern — `createComposerHandle` / `createComposerHandleBinding` (src/plugins/behaviour/composer-handle.ts, with an optional handle-subtype type parameter for channels whose handle carries methods) — and every channel is a configuration of it, never a copied store: the card selection store (above), the drag-drop handle, the word-count handle, the tk handle, and the footnote handle. The drag-drop handle (src/plugins/behaviour/dragDropHandle.ts) owns the editor container element, the DragDropHandler, and the isDragging flag: fed at mount by InklingComposableEditor and DragDropReorderPlugin, with the isDragging truth published by the handler itself through its `onDraggingChange` port (the owner publishes; no adapter mirrors), read synchronously by useCardDragAndDrop and useGalleryReorder — hooks register through the useDragDropContainer adapter when the handler appears instead of relying on plugin-before-children mount order — and subscribed render-only by card chrome (InklingCardWrapper, ActionToolbar) for isDragging. All five handles are created and provided by one `ComposerHandlesProvider` (src/context/ComposerHandlesProvider.tsx); React subscribes through the context bindings (`useDragDropHandleState`, `useCardSelectionState`, …) directly — the alias-hook layer is gone. The word-count handle (src/plugins/behaviour/wordCountHandle.ts) owns the top-level WordCountPlugin's onChange callback: fed at mount by that plugin, subscribed render-only by InklingNestedComposer via useWordCountCallback, which mounts a nested WordCountPlugin reactively when the callback lands instead of reading a shared ref once at render time. The tk handle (src/plugins/behaviour/tkHandle.ts) owns the per-editor TK node map plus the throttled derivation of `tkNodeMap`/`tkCount`: fed by TKPlugin's TKNode mutation listener and its unmount cleanup (`removeEditor`), read synchronously by TKPlugin's listeners, subscribed render-only by TKPlugin (indicators) and TKCountPlugin via `useTKHandleState`; its context binding is `src/context/TKHandleContext.tsx`. The footnote handle (src/plugins/behaviour/footnoteHandle.ts) owns the render-time maps the definition rows subscribe to (targetKey → 1-based visible index, targetKey → definition node key — the rows are chrome and must not walk the tree themselves) plus the focus-handoff request the caret trigger files for a freshly created definition (the row's nested editor does not exist at insert time, so the request waits for the row to mount and claim it): fed by FootnotePlugin, subscribed render-only via useFootnoteHandleState.
_Avoid_: context mutation channel, shared ref

**Reorder rules**:
The one pure module owning drag-reorder and drop-allowance decisions (src/utils/draggable/reorder-rules.ts): `resolveReorder` / `resolveDrop` / `isReorderAllowed` decide from geometry and indices alone, behind the `ReorderGeometry` seam (`createReorderGeometry(container, droppableSelector)`), so the rules carry unit tests and the DOM stays at the edges. `DragDropReorderPlugin` and `useGalleryReorder` are adapters over it — the previous third drop-allowance implementation is gone, and `insertIndex` derivation (with `adjustInsertIndexForRemoval`) lives in exactly one place. The derivation travels as the **drop resolution** (`DropResolution`, DragDropContainer.ts): `getIndicatorPosition`'s answer is kept on the handler's drag state and passed to `onDrop` as a required argument — what the indicator showed is exactly what the drop consumes, never ambient state on `DraggableInfo`; a null resolution is an explicit, typed input (the card container rejects it — no resolution, no drop; the gallery maps it to slot 0 for a container-level drop into an empty gallery). The rules decide; the drop's _application_ (relocation, insertion, source removal) lives in the drop surgery.
_Avoid_: drop logic, drag rules

**Nested-editor protocol**:
The named vocabulary for events crossing editor boundaries (src/plugins/behaviour/nested-editor-protocol.ts): `markEventFromNested` / `markEventFromCaptionEditor` tag a KeyboardEvent at the boundary, `getEventProvenance` reads the tag downstream (`NestedEditorProvenance`), and `isTypeaheadMenuOpen` is the single typeahead-open check. The protocol also owns the nested **Enter hand-off** (`registerNestedEnterHandoff`): the shared typeahead-bail / shift+enter-pass / mark + re-dispatch-to-parent + swallow core behind both nested-editor surfaces' Enter handling, with each caller's divergent branches (ctrl/cmd routing, focusNext) registered before it — and the caption **type-to-focus** policy (`registerCaptionTypeToFocus`): while the parent card is selected and the caption is unfocused, a printable keystroke (no modifiers, not on an input/textarea) focuses the caption editor. Consumers ask the protocol instead of reading monkey-patched flags or re-querying the typeahead menu DOM.
_Avoid_: event flag, nested-event hack

**Upload intent**:
The one media-upload flow module (src/utils/upload-intent.ts): file(s) plus per-card metadata extraction in, a typed node patch out through the card write seam, and the object-URL preview lifecycle created and revoked in one place. Each media card's upload is a configuration of these primitives — per-card variance (metadata extraction, empty-result policy, pre-upload src reset) stays per-card data, never a copied skeleton; all nine intents carry per-card test tables. The video main→thumbnail composition is one flow here (`videoFlowUploadIntent` — main upload, then the synthesized `${file.name}.jpg` thumbnail sub-flow only when a url and a blob exist). The header card's background-image upload is a configuration too (`headerBackgroundUploadIntent`: pre-patch src reset, dimensions read from the result URL, empty result still patches `''`/`0`/`0`). Every metadata extraction (`getImageDimensions`, `getAudioMetadata`, `extractVideoMetadata`) is a thin config over the one **media-load wait** (`awaitMediaEvents`, src/utils/awaitMediaEvents.ts): the element's success events in — several listed events cover blob loads whose `loadedmetadata` + `canplay` arrive in one task, with `start` running after the listeners attach — error or a bounded timeout out, listeners and timer cleaned on settle; the video extractor leases its object URL from the preview-lease seam, so every settle path revokes exactly once. The React side of every media card's upload channel is the **media-card upload wiring** (`useMediaCardUpload`, src/hooks/useMediaCardUpload.ts): the host uploader for one media kind, the file drag handler, the initial-file kickoff, the insert-time dialog trigger, the hidden-input ref, and the files-only change handler — one hook per channel (audio and video compose two), with the card's intent call told which source fired (`input`/`drop`/`initial`, carrying the input-only src reset).
_Avoid_: upload handler, upload helper

**Preview lease**:
The owned lifetime of a blob object URL used as an in-editor preview (src/utils/preview-lease.ts — the one file that calls `URL.createObjectURL`/`URL.revokeObjectURL`, pinned by the upload-preview import guard): created by `createPreviewLease`, released exactly once by `release()` (idempotent), tracked in sets by `createPreviewLeasePool`, bridged to React state by `usePreviewLease`. The upload-intent module is a consumer — each intent leases its preview on start and releases it on settle. Replacing or clearing a preview releases the previous lease; unmounting releases whatever is still held.
_Avoid_: preview URL ref, object-URL ref

**Host card**:
A card the host declares through the public `defineCard` seam (src/nodes/cards/host-cards.ts) instead of the built-in declaration set: one spec (`HostCardSpec`, defined beside the registry that stores it) carries the nodeType, a `generateDecoratorNode`-built base node, the insert/menu/toolbar facts, and the decorate render, and the call returns the assembled node class to compose into `<InklingComposer nodes>` (plus the fence transformer when the spec opts into the markdown round-trip). `defineCard` validates, assembles, and registers — the registry (src/nodes/cards/host-card-registry.ts, kept registry-only so the derived views can read it without import cycles) stores the raw spec verbatim, complete at registration, and every derived view projects its own shape off it through the same projectors the built-in declarations use (the assembled class never rides the record; the views derive it through the memoized assembler). The derived views intersect with each editor's registered node types, so a host card only appears on surfaces that composed its node in. `defineCard` runs at module top level, before the composer mounts.
_Avoid_: custom card, external card

**Host config**:
The closed, per-area-sliced config a host hands `<InklingComposer cardConfig={...}>` — the exported `CardConfig` composed from `GifSettings`, `SnippetSettings`, `LinkingSettings`, `UploadSettings`, `MathSettings`, `LibrarySettings` (src/context/InklingHostIntegrationContext.tsx): gif provider keys, snippet storage callbacks, link search/embed/autocomplete hooks, image upload constraints, the math preview channel (`renderMath` — the host's server-side KaTeX render for in-editor previews; the artifacts persisted on math nodes stay host-filled, never written back by the editor), and the media library callbacks (`imageLibrary` search/upload — the image-library picker's data channel; see "Media library"). Every key the editor reads is declared; unknown keys are compile errors. The exported name stays `CardConfig` — the host-facing name the demo, docs, and internal readers already use — even though the glossary forbids "card config" as a term for card spec: this bag configures the host environment the cards run in, never an individual card's definition.
_Avoid_: options bag, card settings

**Clipboard protocol**:
The one headless module owning the paste pipeline's shared vocabulary (src/plugins/behaviour/clipboard-protocol.ts): the MIME constants, `PASTE_MARKDOWN_COMMAND`, `INSERT_MEDIA_COMMAND`, one per-editor modifier state (`getModifierState(editor)`), and input-side link acceptance. The pipeline: `registerPasteHandler.ts` (entry, `PASTE_COMMAND`) → `plainTextPaste.ts` (shared plain-text classifier) → the link leg (`PASTE_LINK_COMMAND`, already headless in `behaviour/commands.ts`, handled by `registerLinkMatching.ts`), the markdown leg (`PASTE_MARKDOWN_COMMAND` → the headless `markdownToSanitizedHtml` in `behaviour/markdownPaste.ts` → `MarkdownPastePlugin`, which keeps only the DataTransfer glue), and the file leg (`INSERT_MEDIA_COMMAND`; the drop-side claim RULES live in `behaviour/file-drop-routing.ts` — acceptable-mime derivation from the card declarations × host `fileTypes`, first-claimant-wins file matching — while the drop FLOW around them lives in `behaviour/file-drop.ts`: `handleFileDrop` behind its `FileDropPorts`, the DROP_COMMAND → `DRAG_DROP_PASTE` routing of `registerFileDropCommands` — dropped files insert at the selection left behind, never the drop point — and the dragover cursor suppression with its card carve-out in `registerDragOverSuppression`. `DRAG_DROP_PASTE` is borrowed from upstream as the public files-arrived bus (`ExternalControlPlugin.insertFiles` and hosts dispatch it) with exactly one handler, its false return letting host-registered lower-priority handlers also run; `DragDropPastePlugin` keeps only the uploader context and mounts the registration, and `CardInsertPlugin` claims per card). The protocol owns the modifier state's writes as well as its storage: the first `getModifierState(editor)` call for an editor attaches one document keydown/keyup pair writing the single `event.shiftKey` formulation (reading held-state off every key event covers the dual-shift-release corner, so it no longer exists), and the markdown leg's command listener reads the state instead of closing over React state, so Shift press/release no longer re-registers it. There is no listener teardown — Lexical editors have no destroy hook, and the codebase's per-editor WeakMap resources rely on the key's GC; the listeners close over only the state object, never the editor.
_Avoid_: paste utils, clipboard helpers

**Markdown dialect**:
One of the editor's two named markdown import pipelines. The **paste dialect** (`pasteDialect.render`, src/markdown/paste-dialect.ts — `PASTE_MARKDOWN_COMMAND` → `MarkdownPastePlugin`) renders clipboard text through the headless `markdownToSanitizedHtml` (src/plugins/behaviour/markdownPaste.ts): markdown-it (footnote/mark/sub/sup plugins — an engine the markdown card's HTML export also uses) + `sanitizeHtml`, then Lexical HTML import; it speaks footnotes, `==mark==`, `~sub~`, `^sup^`, and has no card-fence grammar, so a pasted ` ```inkling:*``` ` fence becomes a code block card whose language is the fence tag. The **card-aware round-trip dialect** (src/markdown/round-trip.ts — `markdownToLexicalState` / `lexicalStateToMarkdown`) imports and exports through `@lexical/markdown` with the Inkling card transformers; it speaks ` ```inkling:<card>``` ` fences and standard `![alt](src)` image syntax but not footnotes. Both dialects map `==mark==` to highlight and `~`/`^` to sub/superscript, and both serialize code fences through one body (`codeBlockFence` in the card-shortcut seam — `CODE_BLOCK` reads `getTextContent()`, `CODE_FENCE` reads `node.code`; the bracketing strip `stripFenceLines` is shared too). What a dialect speaks lives in its module comment — the former `grammar`-as-data seam had no behavioural consumer and was deleted. Whether the paste path should adopt the card-aware dialect is an open product question (docs/markdown-api.md).
_Avoid_: markdown pipeline, markdown mode

**Card shortcut**:
A typing shortcut that turns the current paragraph into a card — the code fence (` ```lang `) and the horizontal rule (---). One seam module (src/markdown/card-shortcuts.ts) owns each shortcut's trigger regexes and replace-and-select implementation, plus the fence serialization body (`codeBlockFence` — the one code-fence shape both export transformers delegate to, each keeping only its text source) and the bracketing strip (`stripFenceLines`). The call sites keep only their trigger: the enter and tab keys (keyboard-navigation), the markdown shortcut/import transformers (`CODE_BLOCK`/`HR` in src/markdown/transformers.ts), and the HR insert/scan registrations (behaviour/horizontal-rule.ts — `$insertHorizontalRule` for the insert command, `resolveDividerScanTarget` for the per-update scan's caret guard, with HorizontalRulePlugin reduced to a two-effect adapter). Trigger semantics differ on purpose per trigger and are named in the seam rather than flattened — e.g. the fence transformer fires only on the trailing-space keystroke while enter/tab fire regardless of trailing space.
_Avoid_: markdown shortcut, slash command

**Update-scan registration**:
The one registration policy for plugins that scan the document on each content update (src/plugins/behaviour/update-scan.ts): `registerUpdateScan(editor, { dirty, tag, scan })` owns the history-tag skip (historic/history-push/history-merge — undo restores the trigger text, so an ungated scan would resurrect what it replaced), the composing skip, and the empty-dirty skip, then runs the plugin's scan in a nested update (tagged `history-push` for a separate undo entry, untagged to merge with the typing). The per-plugin divergence is exactly two knobs: which dirty sets must be non-empty (`leaves` vs `leaves-or-elements`) and the update tag. `EmEnDashPlugin` and `HorizontalRulePlugin` are the two adapters; HorizontalRulePlugin's scan runs through `registerHorizontalRuleScan` (behaviour/horizontal-rule.ts), whose scan body delegates to the card-shortcut seam. EmEnDash's dash grammar is substantial enough to be headless: `$replaceDashes` (src/plugins/behaviour/em-en-dash.ts) owns the right-to-left scan, boundary guards, HR-shortcut exemption, and caret adjustment as a synchronous test table; the plugin keeps only the `supportsHrShortcut` detection and the registration.
_Avoid_: update listener idiom, scan-on-update

**Footnote ref / footnote definition**:
The two halves of the footnote subsystem (docs/kobato-fit-plan.md C4 §3.2). A **footnote ref** is the inline citation — a TextNode entity (`FootnoteRefNode`, src/nodes/footnote/FootnoteRefNode.ts, TKNode precedent) whose visible text IS the 1-based index; the renumber engine rewrites the text in place, so no separate index field can drift. Its `targetKey` points at the definition it cites. A **footnote definition** is the cited content — a menu-less card (`footnotedefinition` declaration) living in the doc-end definition run, with one nested editor (`content`) and the same `targetKey`; its visible index is position-derived (its rank in the run), never stored. The behaviour module (src/plugins/behaviour/footnotes.ts) owns the `^ ` caret trigger (with backslash suppression and the table-cell/code guard), the renumber engine (citation order first, orphan definitions tailed in stored order, wholesale skip when a ref targets a missing definition, signature short-circuit), `$removeFootnote` (definition plus every citing ref; the reverse — deleting the last ref — leaves an orphan by design), and the RootNode transform holding the doc-end-run invariant. The exported `<section class="footnotes">` wrap is a mechanical string-layer step over that invariant (`footnotesSectionTitle` names the heading); the anchor contract (`user-content-fn-N` / `user-content-fnref-N` / `data-footnote-backref`) has a single owner (src/nodes/footnote/footnote-anchors.ts). Import recasts every targetKey per pass (import-is-a-new-entity, src/nodes/footnote/footnote-keys.ts). Known v1 gap: nested editors never insert or number footnotes (registration skips them per editor instance).
_Avoid_: footnote mark, endnote, sidenote

**Artifact slot**:
A card-node property that carries a server-prerendered artifact the editor never produces: the code card's `highlightedHtml` (Shiki HTML) and the math family's `mathml`/`svg` (KaTeX). Inkling never runs Shiki or KaTeX in the browser (CSP) — the host fills the slot on save and the node carries it opaquely through serialization; the in-editor preview stays CodeMirror (code) or the host's `renderMath` channel (math) and never writes back into the slot. The node-level invariant is **edit-invalidates**: the artifact describes the current source, so the base-node setters (`code`/`language` on BaseCodeBlockNode, `tex` on BaseMathNode) clear the slot on change — the node-level equivalent of kobato's stripPrerenderArtifacts — while the constructor and importJSON assign the fields directly, so a host-filled artifact survives deserialization and cloning. Renderers emit a non-empty artifact verbatim through the render context's named sanitize configs (`SHIKI_HTML_CONFIG` / `MATH_HTML_CONFIG`) and fall back to the escaped source when the slot is empty.
_Avoid_: prerender cache, baked preview

**Render-time meta**:
The request-scoped enrichment hook on the export path (`resolveRenderMeta`, declared on `ExportDOMOptions` and mirrored on the render context): a card renderer resolves host data by `(kind, id)` at render time, an unresolved pair returns undefined, and the card falls back to its placeholder. Synchronous by contract — exportDOM is a synchronous pipeline, so the host resolves before rendering (kobato prerenders its music-player meta, then renders) and async fetching never happens mid-render. The data is request-scoped and never persisted on the node. The music player card itself is a host card (defineCard); this hook is its render-side prerequisite — inkling core ships no music card.
_Avoid_: SSR fetch, async enrichment

**Selection-anchored popup**:
A popup laid out against an anchor rect. One module owns every popup's placement (src/utils/selection-anchored-popup.ts) in two positioning modes: **fixed** (viewport coords, spans the container's width, flips above the anchor when the popup plus its max-height budget would overflow the scroll container — the at-link results popup and the link-action toolbar; the budget `popupMaxHeightBudget` = results-list `POPUP_LIST_MAX_HEIGHT_VH` + `POPUP_TOOLBAR_HEIGHT_PX`, single-sourced with the CSS-side max height) and **absolute** (parent-relative offsets at natural width — the slash card menu's `below` edge with the `measured` flip, and the plus button's `at-anchor` edge with no flip). The two anchor adapters (`createNodeElementAnchor`, `createSelectionAnchor`) live beside the rules.

# Inkling Editor

A Lexical-based rich-text editor built around cards — block-level embeds (image, video, button, bookmark, …) that live inside the document but behave as atomic units.

## Language

**Card**:
A block-level embed in the document (image, video, gallery, button, bookmark, callout, toggle, header, file, audio, html, code block, horizontal rule, math). Atomic from the writer's perspective: selected as a unit, deleted as a unit. The table element family is deliberately not a card — its cells hold editable inline text with a real Lexical selection, which the decorator card pipeline cannot provide — so "card" never names tables.
_Avoid_: decorator, embed, block

**Card adjacency**:
The state of the caret or selection sitting immediately before or after a card. Comes in two notions: **visual adjacency** (the caret's rendered position, derived from geometry — what arrow keys care about) and **logical adjacency** (the selection anchor's offset — what backspace/delete care about).
_Avoid_: next-to-card, beside-card

**Card spec**:
The declarative definition of a card — its properties, card menu, nested editors, and transient state — from which the card's node behaviour is produced. Simple cards are nothing but their spec. The transient/nested-editor field vocabulary is single-sourced from the spec at the type level too: the spec arrays are `as const satisfies` on the declaration, and `CardSpecFieldMap<typeof declaration, Values>` (exported from the public barrel, defined beside the generator) derives the shim's `__*` field names from the spec's literal keys — renaming a spec entry is a compile error at the shim (the per-field value types stay hand-written in the `Values` argument; the base class's `declare __*` leg cannot derive, so `test/typecheck/card-spec-field-agreement.ts` pins it, and `card-declarations.test.ts` pins the constructed/dataset agreement at runtime).
_Avoid_: card config, card definition

**Card declaration**:
The single per-card source of truth naming everything the editor must know about a card: its card spec, whether it joins the markdown round-trip (the `markdown` flag), its insert-command registration (command, edit-mode flag, media claiming), its toolbar label (`toolbarLabel` — the `data-inkling-card-toolbar` selector contract), and, for the four media cards, its `uploadType`. The declarations come from two sources read together: the closed built-in set `CARD_DECLARATIONS` and the host cards' registry (`getHostCards()`, src/nodes/cards/host-card-registry.ts). Every registry is a derived view over the card declarations — the node sets (`getEditorCardNodes`), the menus, the decorate targets, the insert registrar (`CardInsertPlugin`), the toolbar labels (src/nodes/cards/card-toolbar-labels.ts), and the markdown fence payloads (src/nodes/cards/card-markdown-transformers.ts). Every derived view resolves its card facts through one merge-policy module — `resolveCardFacts` / `resolveAllCardFacts` (src/nodes/cards/card-facts.ts): built-in declaration first, host registry fallback, so the "host cards never override built-ins" invariant has exactly one home and each view keeps only its own field projection.
_Avoid_: card registration, card manifest

**Editor surface**:
One of the shipped top-level editor compositions — the default editor (`InklingEditor`) and the markdown round-trip. Each is a preset over the shared composer: its own node set (derived from `EDITOR_BASE_NODES`), its feature plugins (`DEFAULT_FEATURE_PLUGINS`), its markdown transformers. A card declaration's `markdown` flag names whether the card joins the round-trip; there is no runtime surface query — a card is present on a surface because that surface composed its node in. `InklingSurface` (src/components/InklingSurface.tsx) is the composition rule made exportable: a custom host surface wraps its top-level editor tree in exactly one (inside an `InklingComposer`), so nested card editors share the top-level undo stack and `onChange`. The published package layers the surfaces across two entries: `.` carries the full editor, while `./core` (plan C5) ships only the card-free composition pieces — the core `InklingComposer` (required `nodes`), `InklingSurface`, `InklingComposableEditor`, `RestrictContentPlugin`, and the `MINIMAL`/`BASIC` node and transformer sets.
_Avoid_: environment, platform

**Import spec**:
The card declaration's DOM-import knowledge — how the card's markup reads back into node state on HTML import/paste: declarative conversion entries (tag, priority, guard, per-property reads) defined beside the card's `properties` in its base node module, from which the generated node machinery derives `importDOM`. The generator throws at class-creation time when a read names an unknown property. Cards whose parsing is structural (collection payloads, sibling walking, DOM mutation, derived payloads) keep hand-written parsers.
_Avoid_: import parser, DOM conversion config

**Render context**:
The read-only, per-render-pass view of export-time policy and data that is the sole export-time view a card renderer receives besides the node: URL safety, sanitization, feature flags, color checks, document resolution, heading-id tracking, image/markdown data options, render-time meta resolution. The public entry points (`exportDOM(editor, options)`, `$convertToHtmlString`, `LexicalHTMLRenderer.render`) still accept the export options and build the context from them. Card sources must not import the policy modules directly — an import guard enforces the seam.
_Avoid_: options bag, policy object

**Headless HTML surface**:
The public headless conversion pair-plus-one (`lexicalStateToHtml` / `htmlToLexicalState` / `lexicalStateToPlainText`, src/html/headless-html.ts) — one stateless function per direction over the internal renderer (`LexicalHTMLRenderer`) and importer (`htmlToLexical`), named to mirror the markdown pair. Both HTML directions resolve their DOM through the headless DOM port; the plain-text direction needs no DOM and stays synchronous. Node-set semantics differ by direction on purpose (renderer `nodes` additive, importer `editorConfig.nodes` wholesale replacement) — documented, not unified.
_Avoid_: renderer class export, HTML round-trip module

**Headless DOM port**:
The only module in the package that knows jsdom (src/html/headless-dom.ts): `resolveHeadlessDom(injected?, load?)` resolves the `ExportDOMDom` for one headless conversion — an injected `options.dom` first, then the global `window.document` (mirroring the render context's createDocument chain), then a lazily imported, process-cached JSDOM, throwing an error naming the optional `jsdom` peer on failure. The jsdom loader hides behind the `load` injection port, so the failure leg is a synchronous test table. No other module may import jsdom — an import guard enforces it.
_Avoid_: jsdom imports in conversion modules, per-module DOM sniffing

**Export-time image sizing**:
The one module owning export-time img dimension policy (src/nodes/base/utils/export-image-sizing.ts): `getExportImageDimensions` returns the resized width/height when the shrink policy applies (`defaultMaxWidth` set, the intrinsic width exceeds it, and the image is local and transformable) or `null` to keep intrinsic dims. The image and gallery renderers are the two adapters; their `sizes`-attribute rules stay per-card data.
_Avoid_: resize helper, sizing logic

**Card write seam**:
The typed write path for card-node fields: `$updateCardNode(nodeKey, guard, update)` (src/nodes/base/update-card-node.ts), called inside `editor.update()`. The card's own `$is*` guard narrows the node, so every field the mutator writes is checked against the card's node type. The React-side invocation idiom has one home beside the seam: `useCardWriter(nodeKey, guard)` (src/hooks/useCardWriter.ts) owns `editor.update` + `$updateCardNode` + the guard and returns a `write(mutator)` the card component calls per mutation — the five-line ceremony is never re-typed at a call site.
_Avoid_: `$getNodeByKey` + `as GeneratedDecoratorNodeBase`

**Card selection store**:
The per-top-level-composer, editor-side store owning card-selection truth for non-React code: the selected card key and the edit-mode flag. Built on the composer handle factory; fed by registerCardSelection and the card command handlers, read synchronously by command handlers, subscribed to render-only by React via useCardSelection. There is no per-feature selection context — the former `InklingSelectedCardContext` folded into this store.
_Avoid_: selection context, selection mirror, selected-card state

**Composer handle**:
A per-top-level-composer, editor-side channel in the card-selection-store shape (getState / setState(partial) / subscribe, reference-equality change guard, render-only useSyncExternalStore binding, one provider-created instance with a module-default fallback) for values non-React code must read synchronously. One factory owns the pattern — `createComposerHandle` / `createComposerHandleBinding` (src/plugins/behaviour/composer-handle.ts, with an optional handle-subtype type parameter for channels whose handle carries methods) — and every channel is a configuration of it, never a copied store: the card selection store (above), the drag-drop handle, the word-count handle, the tk handle, and the footnote handle. The drag-drop handle (src/plugins/behaviour/dragDropHandle.ts) owns the editor container element, the DragDropHandler, and the isDragging flag: fed at mount by InklingComposableEditor and DragDropReorderPlugin (which also flips isDragging on drag start/end), read synchronously by useCardDragAndDrop and useGalleryReorder — hooks register through the useDragDropContainer adapter when the handler appears instead of relying on plugin-before-children mount order — and subscribed render-only by card chrome (InklingCardWrapper, ActionToolbar) for isDragging. The word-count handle (src/plugins/behaviour/wordCountHandle.ts) owns the top-level WordCountPlugin's onChange callback: fed at mount by that plugin, subscribed render-only by InklingNestedComposer via useWordCountCallback, which mounts a nested WordCountPlugin reactively when the callback lands instead of reading a shared ref once at render time. The tk handle (src/plugins/behaviour/tkHandle.ts) owns the per-editor TK node map plus the throttled derivation of `tkNodeMap`/`tkCount`: fed by TKPlugin's TKNode mutation listener and its unmount cleanup (`removeEditor`), read synchronously by TKPlugin's listeners, subscribed render-only by TKPlugin (indicators) and TKCountPlugin via `useTKHandleState`; its context binding is `src/context/TKHandleContext.tsx`. The footnote handle (src/plugins/behaviour/footnoteHandle.ts) owns the render-time maps the definition rows subscribe to (targetKey → 1-based visible index, targetKey → definition node key — the rows are chrome and must not walk the tree themselves) plus the focus-handoff request the caret trigger files for a freshly created definition (the row's nested editor does not exist at insert time, so the request waits for the row to mount and claim it): fed by FootnotePlugin, subscribed render-only via useFootnoteHandleState.
_Avoid_: context mutation channel, shared ref

**Reorder rules**:
The one pure module owning drag-reorder and drop-allowance decisions (src/utils/draggable/reorder-rules.ts): `resolveReorder` / `resolveDrop` / `isReorderAllowed` decide from geometry and indices alone, behind the `ReorderGeometry` seam (`createReorderGeometry(container, droppableSelector)`), so the rules carry unit tests and the DOM stays at the edges. `DragDropReorderPlugin` and `useGalleryReorder` are adapters over it — the previous third drop-allowance implementation is gone, and `insertIndex` derivation (with `adjustInsertIndexForRemoval`) lives in exactly one place. The rules decide; the drop's _application_ (relocation, insertion, source removal) lives in the drop surgery.
_Avoid_: drop logic, drag rules

**Nested-editor protocol**:
The named vocabulary for events crossing editor boundaries (src/plugins/behaviour/nested-editor-protocol.ts): `markEventFromNested` / `markEventFromCaptionEditor` tag a KeyboardEvent at the boundary, `getEventProvenance` reads the tag downstream (`NestedEditorProvenance`), and `isTypeaheadMenuOpen` is the single typeahead-open check. The protocol also owns the nested **Enter hand-off** (`registerNestedEnterHandoff`): the shared typeahead-bail / shift+enter-pass / mark + re-dispatch-to-parent + swallow core behind both nested-editor surfaces' Enter handling, with each caller's divergent branches (ctrl/cmd routing, focusNext) registered before it. Consumers ask the protocol instead of reading monkey-patched flags or re-querying the typeahead menu DOM.
_Avoid_: event flag, nested-event hack

**Upload intent**:
The one media-upload flow module (src/utils/upload-intent.ts): file(s) plus per-card metadata extraction in, a typed node patch out through the card write seam, and the object-URL preview lifecycle created and revoked in one place. Each media card's upload is a configuration of these primitives — per-card variance (metadata extraction, empty-result policy, pre-upload src reset) stays per-card data, never a copied skeleton. The header card's background-image upload is a configuration too (`headerBackgroundUploadIntent`: pre-patch src reset, dimensions read from the result URL, empty result still patches `''`/`0`/`0`).
_Avoid_: upload handler, upload helper

**Preview lease**:
The owned lifetime of a blob object URL used as an in-editor preview: created by `createPreviewLease`, released exactly once by `release()` (idempotent), bridged to React state by `usePreviewLease`. Replacing or clearing a preview releases the previous lease; unmounting releases whatever is still held.
_Avoid_: preview URL ref, object-URL ref

**Host card**:
A card the host declares through the public `defineCard` seam (src/nodes/cards/host-cards.ts) instead of the built-in declaration set: one spec carries the nodeType, a `generateDecoratorNode`-built base node, the insert/menu/toolbar facts, and the decorate render, and the call returns the assembled node class to compose into `<InklingComposer nodes>` (plus the fence transformer when the spec opts into the markdown round-trip). Its declaration lives in the host registry (src/nodes/cards/host-card-registry.ts) and is read by every derived view together with the built-in card declarations; the derived views intersect with each editor's registered node types, so a host card only appears on surfaces that composed its node in. `defineCard` runs at module top level, before the composer mounts.
_Avoid_: custom card, external card

**Host config**:
The closed, per-area-sliced config a host hands `<InklingComposer cardConfig={...}>` — the exported `CardConfig` composed from `GifSettings`, `SnippetSettings`, `LinkingSettings`, `UploadSettings`, `MathSettings`, `LibrarySettings` (src/context/InklingHostIntegrationContext.tsx): gif provider keys, snippet storage callbacks, link search/embed/autocomplete hooks, image upload constraints, the math preview channel (`renderMath` — the host's server-side KaTeX render for in-editor previews; the artifacts persisted on math nodes stay host-filled, never written back by the editor), and the media library callbacks (`imageLibrary` search/upload — the image-library picker's data channel; see "Media library"). Every key the editor reads is declared; unknown keys are compile errors. The exported name stays `CardConfig` — the host-facing name the demo, docs, and internal readers already use — even though the glossary forbids "card config" as a term for card spec: this bag configures the host environment the cards run in, never an individual card's definition.
_Avoid_: options bag, card settings

**Clipboard protocol**:
The one headless module owning the paste pipeline's shared vocabulary (src/plugins/behaviour/clipboard-protocol.ts): the MIME constants, `PASTE_MARKDOWN_COMMAND`, `INSERT_MEDIA_COMMAND`, one per-editor modifier state (`getModifierState(editor)`), and input-side link acceptance. The pipeline: `registerPasteHandler.ts` (entry, `PASTE_COMMAND`) → `plainTextPaste.ts` (shared plain-text classifier) → the link leg (`PASTE_LINK_COMMAND`, already headless in `behaviour/commands.ts`, handled by `registerLinkMatching.ts`), the markdown leg (`PASTE_MARKDOWN_COMMAND` → the headless `markdownToSanitizedHtml` in `behaviour/markdownPaste.ts` → `MarkdownPastePlugin`, which keeps only the DataTransfer glue), and the file leg (`INSERT_MEDIA_COMMAND`; the drop-side claim routing lives in `behaviour/file-drop-routing.ts` — acceptable-mime derivation from the card declarations × host `fileTypes`, first-claimant-wins file matching — while `DragDropPastePlugin` keeps only the DOM glue and the dispatch, and `CardInsertPlugin` claims per card). The protocol owns the modifier state's writes as well as its storage: the first `getModifierState(editor)` call for an editor attaches one document keydown/keyup pair writing the single `event.shiftKey` formulation (reading held-state off every key event covers the dual-shift-release corner, so it no longer exists), and the markdown leg's command listener reads the state instead of closing over React state, so Shift press/release no longer re-registers it. There is no listener teardown — Lexical editors have no destroy hook, and the codebase's per-editor WeakMap resources rely on the key's GC; the listeners close over only the state object, never the editor.
_Avoid_: paste utils, clipboard helpers

**Markdown dialect**:
One of the editor's two named markdown import pipelines, each a real module whose `grammar` declares what it speaks as data (the shared `MarkdownDialect`/`MarkdownDialectGrammar` seam lives in src/markdown/dialects.ts). The **paste dialect** (`pasteDialect`, src/markdown/paste-dialect.ts — `PASTE_MARKDOWN_COMMAND` → `MarkdownPastePlugin`) renders clipboard text through the headless `markdownToSanitizedHtml` (src/plugins/behaviour/markdownPaste.ts): markdown-it (footnote/mark/sub/sup plugins — an engine the markdown card's HTML export also uses) + `sanitizeHtml`, then Lexical HTML import; it speaks footnotes, `==mark==`, `~sub~`, `^sup^`, and has no card-fence grammar, so a pasted ` ```inkling:*``` ` fence becomes a code block card whose language is the fence tag. The **card-aware round-trip dialect** (`roundTripDialect`, src/markdown/round-trip.ts — `markdownToLexicalState` / `lexicalStateToMarkdown`) imports and exports through `@lexical/markdown` with the Inkling card transformers; it speaks ` ```inkling:<card>``` ` fences and standard `![alt](src)` image syntax but not footnotes. Both dialects map `==mark==` to highlight and `~`/`^` to sub/superscript. Whether the paste path should adopt the card-aware dialect is an open product question (docs/markdown-api.md).
_Avoid_: markdown pipeline, markdown mode

**Card shortcut**:
A typing shortcut that turns the current paragraph into a card — the code fence (` ```lang `) and the horizontal rule (---). One seam module (src/markdown/card-shortcuts.ts) owns each shortcut's trigger regexes and replace-and-select implementation; the call sites keep only their trigger: the enter and tab keys (keyboard-navigation), the markdown shortcut/import transformers (`CODE_BLOCK`/`HR` in src/markdown/transformers.ts), and the HR per-update scan (HorizontalRulePlugin). Trigger semantics differ on purpose per trigger and are named in the seam rather than flattened — e.g. the fence transformer fires only on the trailing-space keystroke while enter/tab fire regardless of trailing space.
_Avoid_: markdown shortcut, slash command

**Update-scan registration**:
The one registration policy for plugins that scan the document on each content update (src/plugins/behaviour/update-scan.ts): `registerUpdateScan(editor, { dirty, tag, scan })` owns the history-tag skip (historic/history-push/history-merge — undo restores the trigger text, so an ungated scan would resurrect what it replaced), the composing skip, and the empty-dirty skip, then runs the plugin's scan in a nested update (tagged `history-push` for a separate undo entry, untagged to merge with the typing). The per-plugin divergence is exactly two knobs: which dirty sets must be non-empty (`leaves` vs `leaves-or-elements`) and the update tag. `EmEnDashPlugin` and `HorizontalRulePlugin` are the two adapters. HorizontalRulePlugin's scan body stays plugin-side — it only delegates to the card-shortcut seam. EmEnDash's dash grammar is substantial enough to be headless: `$replaceDashes` (src/plugins/behaviour/em-en-dash.ts) owns the right-to-left scan, boundary guards, HR-shortcut exemption, and caret adjustment as a synchronous test table; the plugin keeps only the `supportsHrShortcut` detection and the registration.
_Avoid_: update listener idiom, scan-on-update

**Footnote ref / footnote definition**:
The two halves of the footnote subsystem (docs/kobato-fit-plan.md C4 §3.2). A **footnote ref** is the inline citation — a TextNode entity (`FootnoteRefNode`, src/nodes/footnote/FootnoteRefNode.ts, TKNode precedent) whose visible text IS the 1-based index; the renumber engine rewrites the text in place, so no separate index field can drift. Its `targetKey` points at the definition it cites. A **footnote definition** is the cited content — a menu-less card (`footnotedefinition` declaration) living in the doc-end definition run, with one nested editor (`content`) and the same `targetKey`; its visible index is position-derived (its rank in the run), never stored. The behaviour module (src/plugins/behaviour/footnotes.ts) owns the `^ ` caret trigger (with backslash suppression and the table-cell/code guard), the renumber engine (citation order first, orphan definitions tailed in stored order, wholesale skip when a ref targets a missing definition, signature short-circuit), `$removeFootnote` (definition plus every citing ref; the reverse — deleting the last ref — leaves an orphan by design), and the RootNode transform holding the doc-end-run invariant. The exported `<section class="footnotes">` wrap is a mechanical string-layer step over that invariant (`footnotesSectionTitle` names the heading); the anchor contract (`user-content-fn-N` / `user-content-fnref-N` / `data-footnote-backref`) has a single owner (src/nodes/footnote/footnote-anchors.ts). Import recasts every targetKey per pass (import-is-a-new-entity, src/nodes/footnote/footnote-keys.ts). Known v1 gap: nested editors never insert or number footnotes (registration skips them per editor instance).
_Avoid_: footnote mark, endnote, sidenote

**Artifact slot**:
A card-node property that carries a server-prerendered artifact the editor never produces: the code card's `highlightedHtml` (Shiki HTML) and the math family's `mathml`/`svg` (KaTeX). Inkling never runs Shiki or KaTeX in the browser (CSP) — the host fills the slot on save and the node carries it opaquely through serialization; the in-editor preview stays CodeMirror (code) or the host's `renderMath` channel (math) and never writes back into the slot. The node-level invariant is **edit-invalidates**: the artifact describes the current source, so the base-node setters (`code`/`language` on BaseCodeBlockNode, `tex` on BaseMathNode) clear the slot on change — the node-level equivalent of kobato's stripPrerenderArtifacts — while the constructor and importJSON assign the fields directly, so a host-filled artifact survives deserialization and cloning. Renderers emit a non-empty artifact verbatim through the render context's named sanitize configs (`SHIKI_HTML_CONFIG` / `MATH_HTML_CONFIG`) and fall back to the escaped source when the slot is empty.
_Avoid_: prerender cache, baked preview

**Render-time meta**:
The request-scoped enrichment hook on the export path (`resolveRenderMeta`, declared on `ExportDOMOptions` and mirrored on the render context): a card renderer resolves host data by `(kind, id)` at render time, an unresolved pair returns undefined, and the card falls back to its placeholder. Synchronous by contract — exportDOM is a synchronous pipeline, so the host resolves before rendering (kobato prerenders its music-player meta, then renders) and async fetching never happens mid-render. The data is request-scoped and never persisted on the node. The music player card itself is a host card (defineCard); this hook is its render-side prerequisite — inkling core ships no music card.
_Avoid_: SSR fetch, async enrichment

**Selection-anchored popup**:
A fixed-position popup laid out against an anchor rect — the at-link results popup and the link-action toolbar. One module owns the layout (src/utils/selection-anchored-popup.ts): the below-the-anchor default with an above-the-anchor flip when the popup plus its max-height budget would overflow the scroll container, the budget itself (`popupMaxHeightBudget` = results-list `POPUP_LIST_MAX_HEIGHT_VH` + `POPUP_TOOLBAR_HEIGHT_PX`, single-sourced with the CSS-side max height), and the two anchor adapters (`createNodeElementAnchor`, `createSelectionAnchor`). The flip rules take rects as plain data so they are unit-testable without layout; `useSelectionAnchoredPopup` (src/hooks) is the React adapter owning measuring, style writes, and the reposition subscription set (`usePopupRepositionSubscriptions`: window resize, container scroll, popup content mutations — also used by FloatingToolbar).
_Avoid_: floating popup, dropdown positioning

**Floating panel**:
The draggable settings panel a card opens beside itself. One module owns its layout decisions (src/utils/floating-panel.ts): the clamp math (`clampWithinSpacing` / `clampOnDrag` / `clampOnResize` — minimum spacing honouring the panel's previous spacing, then the hard drag boundary), the card-origin resolution (a transformed card, e.g. wide, becomes the coordinate origin), the initial placement (below the card on mobile, right of the card centered on its visible height on desktop), viewport-growth drift back towards that placement, and the headless **drag session** (`createDragSession`: start threshold → move → end, with the scroll/selection/pointer suppression declared behind effect ports). `useFloatingPanel` (src/hooks) is the single React adapter owning the DOM ports (body-level pointer listeners, the user-select stylesheet, click suppression, the panel and scroll-container ResizeObservers); SettingsPanel is its sole consumer. It replaces the former useMovable/useSettingsPanelReposition stack — two stacked single-consumer seams whose tests went around the seam.
_Avoid_: movable, draggable panel

**Link-editing flow**:
The headless module (src/plugins/behaviour/link-editing.ts) owning the link apply/read surgery and the floating-toolbar session. `$applyLinkToSelection(editor, url)` is the single apply-link-then-collapse-selection implementation (previously copy-pasted across the format toolbar, the link-action toolbar, and — a variant — the floating link toolbar); `$removeLink(editor, linkNode)` is the remove-link surgery; `$getLinkHrefAtSelection()` reads the href of the link at the selection; `$selectLinkText(linkNode)` selects a link's full text for editing. The **toolbar session** (`createToolbarSession`, built on the composer-handle factory) is the state machine behind the floating toolbars: `hidden | text | link | snippet`, where selection sync only acts while hidden/text — a link or snippet toolbar stays open across selection changes and closes only through its own actions. The session also owns hovered-link truth: a `hoveredLink` slot that is non-null only while `type === 'hidden'` (suppression is a consequence of state, never a coordination prop), fed by the headless `createLinkHoverFeed` (debounced mousemove in through a port, link resolution inside `editor.read()`), while `createToolbarRevealFeed` owns the format toolbar's reveal gesture (5px move threshold + mouseup-inside-selection) behind effect ports. The selection feed is headless too: `registerToolbarSelectionSync(editor, session)` owns the classifier feeding the machine — composing skip, outside-editor close via native-selection containment, at-link-search suppression, `textSelected`/`href` derivation — over one document `selectionchange` listener. FloatingToolbarPlugin keeps the DOM wiring and renders the machine's state; the toolbar components are render adapters.
_Avoid_: link toolbar state, toggle-link surgery

**Card-menu session**:
The popup-session behaviour shared by the slash and plus card menus (src/hooks/useCardMenuSession.ts): the **cursor lease** (a native Range saved while the menu is open — `saveCursor` — and restored on demand), the close policy (Escape closes _and_ restores the cursor because Escape always blurs the contenteditable; outside-mousedown and the plugins' other closes leave the cursor alone; every close releases the lease), and insert-and-close. The native Selection arrives through an injected adapter so the close policy is unit-testable without a plugin mount. The plugins keep only their DOM event wiring, anchoring, and rendering — the trigger policy itself lives in the card-menu trigger; the plus button's anchor range stays plugin state, leased to the session when the menu opens. Menu data is a derived **sectioned** view end-to-end: `buildCardMenu` returns `sections` (primary, ordered) with `items`/`maxItemIndex` derived from it sharing item identity, and `CardMenu` renders `sections` directly — there is no Map view or re-grouping downstream. The slash menu's keyboard navigation is a headless **menu navigator** (src/hooks/card-menu-navigation.ts — `createMenuNavigator`: wrap-around index, reset-on-rebuild, scroll-request latch, `selectedItem`), consumed via `useSyncExternalStore`; the slash plugin keeps only its command registrations.
_Avoid_: menu popup state, slash menu session

**Snippet insertion**:
The headless module (src/plugins/behaviour/snippet-insertion.ts) behind `InklingSnippetPlugin`. A snippet is a host-managed fragment of serialized editor state — the `{ name, value }` insertParams a snippet menu entry dispatches through `buildCardMenu` — and `$insertSnippet(editor, dataset)` parses the value, regenerates the nodes, and splices them at the selection: a single-card snippet routes through the card insert command so it lands like any other card insert, and a snippet whose last node is a card gets the trailing paragraph (`$ensureParagraphAfterCard`). Malformed host data no-ops silently; the plugin keeps only the command registration.
_Avoid_: snippet handler, template insertion

**Search coordinator**:
The headless module (src/hooks/search-coordinator.ts) owning the link-search flow: two request tracks — the debounced query search and the default-options prefetch — the URL short-circuit (URL-shaped queries skip the search and show the "Link to web page" option immediately), and the cross-track waiting (an empty query waits for the prefetch). Race policy (stale responses never overwrite newer ones, superseded queries, rejections preserve the last options, undefined resolves like a cancellation) lives behind injected ports — the scheduler and the searchLinks promise factory — so the race matrix is a synchronous test table. `useSearchLinks` is the thin React adapter: it recreates the coordinator when the search function or options change, subscribes to its snapshot, and owns only the query-vs-defaults display switch.
_Avoid_: search hook, debounced search

**Drop target**:
A container element that accepts drags and lights up while a droppable drag hovers it. One module owns the drop-target hover seam (src/hooks/useDropTarget.ts): the container element state, the `isDraggedOver` hover flag (set by the hover policy `canDrop` on drag-enter, cleared on leave and on drag end), and the drag-start enablement policy (`adjustEnableOnDragStart`: true enables, false disables, undefined leaves the container's enablement untouched — defaulting to the hover policy). The image card (ImageNodeComponent, gallery-creation drops) and the gallery (useGalleryReorder) are adapters with their own predicates; the gallery's asymmetry is preserved — its hover policy accepts every drag, its enablement policy only enables. The choreography previously existed twice: as the one-consumer useCardDragAndDrop hook and inlined in useGalleryReorder.

**Drop indicator**:

**At-link session**:

**Drag-start session**:

**Card-menu trigger**:

**Initial document**:
The one module owning the minimal valid Inkling document (src/utils/initial-document.ts): `MINIMAL_DOCUMENT` (the full dialect — what an empty live editor's `toJSON()` produces, `textFormat`/`textStyle` included) and `MINIMAL_DOCUMENT_LEGACY_PAYLOAD` (the historical dialect without them — `importJSON` treats the fields as optional, so stored host payloads stay valid; the dialects' relationship is pinned by test), `$appendEmptyParagraph` (the live empty-root repair), and `normalizeInitialEditorState` (the serialized empty-root repair, legacy dialect). `htmlToLexical`, `nested-editors`, `generateEditorState`, and the InklingComposer bootstrap are adapters. **Gif browser**:

**Gallery images mirror**:
The one module owning the gallery card's node↔state sync (src/hooks/gallery-images-mirror.ts): `createGalleryImagesMirror(ports)` — node images in through `readNodeImages` / `subscribeToNodeImages`, the rendered list out as a reference-stable snapshot, `setImages` for local-mutation-plus-node-write, `setPreviewImages` for the local-only preview overlay that never touches the node. **Labels**:
The closed, flat table of every user-visible string the editor chrome renders (src/labels/inkling-labels.ts) — dotted keys (`placeholder.editor`, `menu.image.label`, `action.delete`) with English defaults in `DEFAULT_LABELS`, merged once per composer from the host's partial override table (`<InklingComposer labels={...}>`, `InklingLabelsInput`) into `InklingUiPrefsContext.labels`, and read by components through `useInklingLabels()`. The interface is closed — an unknown override key is a compile error (the host-config closed-bag philosophy) — and interpolation rides plain `string.replace` (`{max}`, `{cardType}`, `{name}`, `{progress}`), never an i18n library. Menu labels are the one indirection: each card declaration's menu entry carries a required `labelKey` beside its English `label`/`desc`, and `buildCardMenu` resolves `menu.${labelKey}.label`/`.desc` at menu-build time through the resolver `useCardMenu` injects from the context — the declared English is the fallback an unresolvable `labelKey` (e.g. a host card's own key) renders. Host cards carry the same required `labelKey`, so the seam is uniform across built-in and host declarations. The Pintura editor is the one nested third-party consumer: the table's `pintura.*` keys feed its `locale` first and `cardConfig.pinturaConfig.locale` spreads on top. Export-renderer strings (video/toggle aria) and host data (snippet names) stay outside the table by design. The full key list is the contract — `test/unit/labels.test.ts` snapshots it, and docs/labels.md is the host-facing reference.
_Avoid_: i18n, translations, locale strings

**Media library**:
The host-driven image-library picker seam (docs/kobato-fit-plan.md C8). The `LibrarySettings` slice of the host config carries one key, `imageLibrary`: a `search` callback (empty query = the default listing, fired immediately on open; non-empty queries debounced at 300ms; `undefined` resolves like a cancellation and keeps the last items) and an optional `upload` callback (the host owns the whole upload UX; its resolution is treated as the selection, `undefined` = cancelled). Open/close state fully reuses the gif picker's transient `selector` overlay mechanism: the image declaration's "Image library" menu entry (gated on the config's presence via `isHidden`) dispatches `OPEN_IMAGE_LIBRARY_COMMAND`, which inserts a placeholder image node carrying `__selector: LibraryPlugin` + `__isImageHidden` — the overlay is open while that node exists; Escape/click-outside dispatch `DELETE_CARD_COMMAND` and the document keeps no trace. A pick maps the item through `toImageDataset` — the flow's only field-mapping point, living in `LibraryPlugin` — and dispatches `INSERT_FROM_LIBRARY_COMMAND`, which shares one insert surgery with `INSERT_FROM_GIF_COMMAND` (build the card from the dataset, `INSERT_CARD_COMMAND`, remove the placeholder); both commands keep their own names for menu/analytics semantics. The headless `createLibraryBrowser<TItem>` state machine (src/utils/services/library-browser.ts — single request track, latest-wins race guard, a rejection keeps the last items and sets `error`; deliberately no pagination, keyboard-navigation machine, or column balancing) is generic over the item shape and exported from both published entries so a host's own library pickers (e.g. music on a host card) reuse it; `useLibraryBrowser` is the thin React adapter and `LibrarySelector` the image-shaped render shell (internal — square tiles with a dims badge, optional upload button, built-in click-outside). The three host-schema keys (`thumbhash`/`storagePath`/`imageId`) ride the image dataset's open index signature as opaque pass-through data: the stock image declaration silently ignores them, and they persist only when the host declares them as properties on its own card declaration. Save-time re-sync against the library (re-resolving fields, writing alt back) is host server logic by design — the editor's responsibility ends at carrying the keys faithfully into the serialized state.
_Avoid_: media manager, asset picker

**Paragraph restriction**:

Same genus as the table cell guard and the footnote doc-end-run invariant, but deliberately NOT a default transform — the headless import path does not enforce it.
_Avoid_: content filter, paragraph-only mode
